# Installing

Four ways in, ordered by how much of the release evidence each one carries through to what you run.
Whichever you pick, the gateway needs a configuration file and its own keys before it will start,
and it should not listen on anything but loopback until you have read
[the operations guide](OPERATIONS.md).

## Evaluate with no install

The fastest path, and the one the evaluation kit exists for. It needs bash and curl, installs a
private copy of the pinned runtime under the extracted folder, and touches nothing else:

```sh
tar xzf egrysa-<tag>-src.tar.gz && cd egrysa-<tag>
./eval-kit/quickstart.sh
```

See [the evaluation kit](../eval-kit/README.md).

## Container, for a deployment

The production path. Deploy by immutable digest, never by tag, after verifying the release:

```sh
tools/verify-release.sh <tag>
# then copy the digest from release-evidence.txt into your manifest
```

The Kubernetes manifests under `deploy/kubernetes/` show the hardened baseline, including the
StatefulSet for several replicas.

## Homebrew

The formula lives in this repository, so there is no second repository to trust:

```sh
brew tap intellumia/egrysa https://github.com/Intellumia/egrysa
brew install intellumia/egrysa/egrysa
egrysa --version
```

Homebrew downloads the standalone binary published with the release and checks it against the hash
in the formula. That hash is generated by `tools/package_release.ts` from the release's signed
`SHA256SUMS`, so it pins an artefact the release evidence covers.

## npm

For teams whose tooling already lives there:

```sh
npm install -g egrysa
egrysa --version
```

The package installs nothing itself. It downloads the same published binary, verifies it against the
same hash, and refuses to install on a mismatch.

## After installing

```sh
egrysa --help
```

A packaged install puts the example configurations beside the binary: under
`$(brew --prefix)/share/egrysa/config` for Homebrew, and in the package's `config` directory for
npm. Copy one, edit it, generate keys, and point `EGRYSA_CONFIG` at it. The configuration schema is
published at `api/config.schema.json` and `deno task config:check` validates a file before you roll
it out.

## What each path gives up

| Path      | Verification you can repeat                                       | Notes                                                                   |
| --------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Source    | Everything: signed tag, signed SBOM, provenance, checksums        | Needs the Deno toolchain, which the kit installs privately if absent    |
| Container | Image signature over an immutable digest, plus SLSA provenance    | The deployment path; digest pinning is on you                           |
| Homebrew  | The formula's hash, which comes from the signed checksum manifest | Homebrew itself becomes part of your supply chain                       |
| npm       | The manifest's hash, which comes from the same place              | npm itself becomes part of your supply chain, and installs run a script |

Neither Homebrew nor npm is where the signatures live. They pin a hash that the signed manifest
covers, which is why the release verification in [RELEASE.md](RELEASE.md) stays the authority.
